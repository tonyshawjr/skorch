# Skorch Security & Coding Audit — 2026-07-22

Read-only multi-agent audit (9 dimensions, each finding adversarially verified). **22 confirmed findings:** 1 critical, 5 high, 6 medium, 8 low, 2 info.

Status column: [ ] open. Fixes should be tested on staging before deploy, like all other changes.

## Remediation status

**Bucket 1 — FIXED & deployed (2026-07-22):** login/register/forgot-password rate limiting (per-IP + per-user/email); constant-time login (no user-enumeration timing); complete logout (session + cookie destroyed); password-reset tokens stored as SHA-256; password reset invalidates all other sessions (users.token_version checked in requireAuth); session fixation on register fixed (session_regenerate_id); XSS on the multiplayer game-over screen escaped (announcer.js). Security headers: verified the platform (CloudPanel front nginx) already sends real X-Frame-Options/nosniff/Referrer-Policy on every response, so the "meta-only" finding was moot; db-secrets.php now returns 404 (nginx deny). HSTS + a real CSP remain open (see LOW findings).

**Bucket 1 (Node) — pending a Render deploy:** roomCode validation (DoS crash), rejoin token (seat hijack), undead-swap actor check, IP rate-limit.

**Bucket 2 — CRITICAL, design stage:** server-authoritative match/Firestorm results. Requires an authenticated-identity layer on the multiplayer server first (players currently send an unverified username).

## [CRITICAL] match.php trusts 100% client-supplied match outcome/stats — unlimited XP/Elo/clan-point farming and unwitting-victim Elo griefing
- **Area:** abuse  ·  **Location:** `server/php/api/match.php:15-26, 31-37, 55, 59-77, 86-98, 144`  ·  **Status:** [ ] open
- **Exploit:** requireAuth() (line 12) only confirms a logged-in session; there is no game/match token tying the request to a real game observed by the Node/Socket.io server. won/game_type/skorches/opponent_name are read straight from the JSON body (lines 15-26) with only (bool)/(int) casts and no per-call bounds. An authenticated attacker POSTs directly to /api/match.php with {"won":true,"game_type":"pvp","opponent_name":"<victim>","skorches":999999}. Lines 31-37 resolve the victim's username to opponent_id with zero verification a match occurred. The Elo branch (line 59 requires game_type pvp/multiplayer AND opponentId — both satisfied) raises the attacker's Elo (line 72) and unconditionally decrements the victim's (line 77, floored only at 100), repeatable in a loop with no rate limit or idempotency key — driving any victim's ranked Elo to 100 without them ever playing. The same request credits the attacker's clan season_points/total_points on a win (lines 93-98) and grants XP including skorches*5 (line 144, here ~5,000,000) feeding awardXP (line 147) and stat-based badge thresholds via checkAndAwardBadges (line 151). total_skorches etc. are also inflated via string interpolation of the int-cast values (line 55).
- **Fix:** Make results server-authoritative: for pvp/multiplayer require a signed one-time match token issued by the Socket.io server when it observes the match end, validated/consumed in match.php instead of trusting won/opponent_id/skorches. For AI mode clamp all per-match counters to plausible maxima and reject out-of-range values; add per-account rate limiting / dedupe by client match UUID. Never let one player unilaterally change another player's Elo — require two-sided reconciliation before crediting.

## [HIGH] match.php lets any authenticated user overwrite another user's ELO/stats/XP/clan points with a fabricated match result
- **Area:** authz  ·  **Location:** `server/php/api/match.php:22-37, 59-99, 147-151`  ·  **Status:** [ ] open
- **Exploit:** A normal registered user logs in and POSTs to /server/php/api/match.php with credentials:'include' and body {"won":true,"game_type":"pvp","opponent_id":<victim_user_id>,"skorches":50}. requireAuth() (auth.php:2-9) only authenticates the CALLER's session; opponent_id is taken verbatim from the client (int-cast at line 22, SQLi-safe but not authorization). The endpoint then: (1) inserts a fabricated match row naming the victim (lines 40-47), (2) raises the attacker's own elo_rating (lines 61-72), (3) at line 77 executes UPDATE stats SET elo_rating=$newOppElo WHERE user_id=$opponentId, driving the victim's rating down toward the 100 floor with no consent or participation from the victim, (4) awards the attacker clan season/total points (lines 86-98), and (5) farms XP/badges (lines 102-151). Verified server/ws/*.js (game-engine.js, game-room.js, index.js) contain no call to match.php and no elo/match-reporting logic, so the Socket.io server is not an authoritative source and match.php trusts the client fully. No match token, no dual-participant confirmation, no rate limiting anywhere. Scriptable thousands of times against any victim id.
- **Fix:** Do not let a client unilaterally assert a PvP/multiplayer result for another user. Make server/ws the source of truth: at match start mint a signed, single-use match token/room record naming both real participant ids; match.php must require and server-side-verify that token (exists, unconsumed, names both userId and opponentId as actual participants), apply ELO/XP/clan changes only then, and mark it consumed. Interim: require both named participants to independently POST a matching result before crediting ELO, and add per-user rate limiting.

## [HIGH] login.php has no rate limiting, attempt counting, or lockout — unlimited-speed credential brute forcing
- **Area:** abuse  ·  **Location:** `server/php/api/login.php:18-26`  ·  **Status:** [ ] open
- **Exploit:** The endpoint does a DB lookup and password_verify() (line 24) with no failed-attempt tracking, IP/account lockout, backoff, or CAPTCHA. grep for rate/throttle/lockout/attempts/captcha across all of server/php returned zero matches, so no shared middleware supplies it either. An attacker scripts repeated POSTs to /api/login.php for a known username at PHP-FPM throughput. Combined with register.php's weak 6-char minimum with no complexity rule (register.php line 31), brute forcing high-value accounts is practical.
- **Fix:** Add a login_attempts store (table or APCu/Redis) keyed by username and/or IP; after ~5 failures in a window return 429 with increasing backoff, reset on success, add CAPTCHA after the first lockout tier.

## [HIGH] firestorm.php 'report' action lets either participant unilaterally declare the winner — first-to-report wins
- **Area:** abuse  ·  **Location:** `server/php/api/firestorm.php:271-290`  ·  **Status:** [ ] open
- **Exploit:** The report handler reads won from the caller's body (line 275), verifies only that the firestorm is active, the match exists, the caller is one of the two participants, and the match isn't already complete (lines 276-283). It then computes winnerId purely from the caller's claim (line 284) and immediately writes winner_user_id and flips status to 'complete' (line 285). No opponent confirmation, no disagreement handling. Player A calls POST /api/firestorm.php?action=report {firestorm_id,seed,won:true} before B reports; the match locks as A's win — B's later truthful report hits the 'complete' guard (line 283) and returns already:true with no override. fsRecomputeScores/fsFinalize (lines 42-67) then credit A's clan +25 season_points/total_points on firestorm completion (line 64).
- **Fix:** Store each side's claimed winner separately, finalize only on agreement, route disagreements to officer/manual review, or tie firestorm results to the same server-authoritative match token recommended for match.php.

## [HIGH] Unvalidated roomCode type-confusion crashes the whole server (unauthenticated single-packet DoS)
- **Area:** node  ·  **Location:** `server/ws/index.js:162 (play-cards), 221 (play-prison), 256 (undead-swap), 297 (rematch); root cause server/ws/game-room.js:53`  ·  **Status:** [ ] open
- **Exploit:** Any client (no auth) connects and emits e.g. socket.emit('rematch', { roomCode: 12345 }) or socket.emit('play-cards', { roomCode: 12345, indexes: [0] }) (indexes passes validateIndexes; roomCode is never checked). getRoom(12345) runs rooms.get((12345)?.toUpperCase()); ?. does NOT short-circuit a non-null number, so (12345).toUpperCase() throws TypeError. Socket.io runs the handler via super.emit inside a process.nextTick with no surrounding try/catch, and there is no process.on('uncaughtException') anywhere in server/ws/*, so the throw is unhandled and Node exits — dropping every connected socket and every in-progress game. play-prison (validates row/index only) and undead-swap (validates nothing) are equally exploitable.
- **Fix:** Add `if (!validateString(roomCode, 4)) return;` at the top of play-cards, play-prison, undead-swap and rematch (matching pickup/chat-message), and harden the choke point: `function getRoom(code){ return typeof code === 'string' ? (rooms.get(code.toUpperCase()) || null) : null; }`. Add a global process.on('uncaughtException') guard as defense-in-depth.

## [HIGH] rejoin-room hijacks a live player's seat and private hand with no token
- **Area:** node  ·  **Location:** `server/ws/index.js:137-156`  ·  **Status:** [ ] open
- **Exploit:** rejoin-room only calls validateString(code,4)/validateString(playerId,10) then unconditionally sets room.players[slotIndex].socketId = socket.id (line 145). playerId is one of the plaintext literals 'player1'/'player2' sent to every client in room-created/room-joined — no secret. There is no check that the slot is actually disconnected (removePlayer sets disconnectedAt but rejoin ignores it) and no rate limit on this handler at all. An attacker who knows a room's 4-char code emits socket.emit('rejoin-room',{code:'ABCD',playerId:'player1'}); the server overwrites player1's socketId with the attacker's, emits state-update containing player1's private hand/prison via getPlayerView, and getPlayerRole thereafter resolves the attacker as 'player', letting them submit moves while the real player is silently locked out.
- **Fix:** Issue a high-entropy per-slot reconnect token (crypto.randomUUID()) at game start, store it server-side, require it in rejoin-room and compare before rebinding socketId. Only permit rejoin when room.players[slotIndex].disconnectedAt is set (slot actually vacated), and apply the per-socket/IP rate limiter to this handler.

## [MEDIUM] Unescaped multiplayer opponent name interpolated into innerHTML on the game-over screen
- **Area:** xss  ·  **Location:** `js/ui/announcer.js:72, 80, 83, 139`  ·  **Status:** [ ] open
- **Exploit:** An attacker joins a multiplayer room and sends an arbitrary `username` string to the socket 'create-room'/'join-room' event. The only server check is validateString(username,20) in server/ws/index.js:20-22 (type + length<=20, no charset filter, no HTML stripping); game-room.js:21,48 stores it verbatim; index.js:360 echoes it in the view payload as opponentName; main.js sets state._opponentName and passes it to showGameOver(...) as opponentName. In announcer.js the raw value (opponent = opponentName) is written unescaped into innerHTML at line 80 (loseSub), line 83 (profile-link text), and line 139 (Add Friend button). This is a genuine unescaped stored-input -> innerHTML sink. Within the hard 20-char server cap, an attacker CAN inject HTML markup, e.g. the 18-char name `<img src=//evil/x>` forces the victim's browser to fetch an attacker-controlled URL when the game-over screen renders (beacon/content-spoof), and other short tags allow limited markup injection. The auditor's stated JS-execution payload `<svg/onload=alert(document.domain)>` is ~35 chars and FAILS the length<=20 check; even a trimmed `<svg onload=alert()>` (20 chars) does not fire via innerHTML in modern browsers (SVG load events do not fire on dynamic fragment insertion), and reliable innerHTML-firing vectors (`<img src=x onerror=a>` = 21 chars, `<iframe onload=...>`) all exceed 20 chars once a handler is included. So arbitrary same-origin JS execution / session impersonation as described is NOT achievable under the actual 20-char cap; the demonstrable impact is markup/HTML injection.
- **Fix:** In js/ui/announcer.js, HTML-escape `opponent` before every interpolation into an innerHTML template (lines ~72/80/83/139) using the existing esc()/escapeHtml() helper (as renderer.js/player-card.js do), or build those nodes with textContent instead of innerHTML. Defense in depth: restrict the socket username charset server-side in server/ws/index.js (e.g. the same [A-Za-z0-9_ ] set used for accounts) so raw HTML can never enter client state.

## [MEDIUM] No rate limiting / lockout on login — unthrottled online brute force
- **Area:** authn  ·  **Location:** `server/php/api/login.php:18-26`  ·  **Status:** [ ] open
- **Exploit:** A grep of the entire server/php tree for throttle|rate_limit|lockout|failed_login|attempt|usleep returns zero matches, and schema.sql has no attempt-tracking column or table. login.php does a single prepared SELECT then password_verify with no counter, delay, or lockout. An attacker scripts unlimited POSTs to /api/login.php against a known username (usernames are public via leaderboard/public-profile.php) at full network speed. Password policy only requires 6 chars (register.php:31), so weak passwords fall quickly to online guessing/credential-stuffing.
- **Fix:** Track failed attempts per-IP and per-username (DB table or cache) with exponential backoff / temporary lockout after N failures in a window, and log repeated failures.

## [MEDIUM] Password reset does not invalidate existing sessions
- **Area:** recovery  ·  **Location:** `server/php/api/reset-password.php:28-38`  ·  **Status:** [ ] open
- **Exploit:** Auth is pure native-PHP sessions keyed only by $_SESSION['user_id'] (middleware/auth.php:2-8; login.php:31 sets it, logout.php:3 destroys only the current session). There is no users.session_version / password_changed_at column and no server-side session store to enumerate — grep for session_version/password_changed returns nothing; the only session_regenerate_id is at login.php:30 (fixation defense, unrelated). reset-password.php updates users.password_hash (line 29-32) and marks the token used (line 34-36), touching neither $_SESSION nor any revocation marker. Concrete flow: attacker obtains the victim's session cookie (shared/public device, XSS, leaked cookie) but not the password. Victim runs forgot-password -> reset-password believing it locks the attacker out. It does not: the attacker's cookie still satisfies isset($_SESSION['user_id']) and authenticates fully, valid up to the 30-day session.gc_maxlifetime set in config.php:3, so access persists after the reset.
- **Fix:** Add a users.session_version (or password_changed_at) column; stamp its value into $_SESSION at login (login.php) and compare it inside requireAuth() (middleware/auth.php); bump it in reset-password.php after the password UPDATE so all pre-existing sessions fail the comparison. As a minimum, record password_changed_at and reject sessions whose stored login time predates it.

## [MEDIUM] register.php and forgot-password.php have no rate limiting — bot account-farming and password-reset email bombing
- **Area:** abuse  ·  **Location:** `server/php/api/register.php:1-87`  ·  **Status:** [ ] open
- **Exploit:** register.php performs only format/uniqueness/age validation (lines 22-49) with no CAPTCHA, email verification, or per-IP throttle, so an attacker scripts unlimited account creation (disposable opponents to feed the match.php Elo/clan exploit, or roster/leaderboard padding). forgot-password.php correctly avoids user enumeration (identical response lines 27 and 63) but has no per-email/per-IP rate limit before mail() (line 61); scripting POSTs with a victim's email fires mail() repeatedly, flooding the victim's inbox at no cost. Verified no rate-limit infrastructure exists anywhere in server/php.
- **Fix:** Add per-IP throttling to both (e.g. 5 registrations/hour/IP, 3 resets/hour/email+IP), cap total reset emails per address per hour independent of IP, and consider email verification before ranked/clan play.

## [MEDIUM] undead-swap lacks actor/turn/one-shot checks — opponent can repeatedly steal prison cards
- **Area:** node  ·  **Location:** `server/ws/index.js:254-274`  ·  **Status:** [ ] open
- **Exploit:** Handler validates only that discardPile top is type 'undead' and that row/index are well-formed. processSpecialEffect's UNDEAD branch (game-engine.js:228-229) sets no state flag, and after an Undead play play-cards calls nextTurn (effect is 'undead', not 'shield'), passing the turn to the opponent. The discard top stays 'undead' until another card covers it. Player B (who never played Undead) then emits socket.emit('undead-swap',{roomCode,myCard:{row:'front',index:0},theirCard:{row:'front',index:1}}); executeUndeadSwap (game-engine.js:308) runs against A's prison with no ownership or turn check, and because no card is discarded by the swap the top stays 'undead', so B can repeat it — unbounded theft/swap from a single Undead play.
- **Fix:** In processSpecialEffect's UNDEAD branch set room.state.pendingUndeadSwap = who; require undead-swap to check room.state.pendingUndeadSwap === who before executing and clear it after one successful swap/take (and whenever any other card is subsequently played).

## [MEDIUM] Low-entropy room codes plus per-socket rate limiting enable private-room brute force
- **Area:** node  ·  **Location:** `server/ws/game-room.js:5-15 (generateCode); server/ws/index.js:40-47 (rateLimit), 138 (rejoin-room unthrottled)`  ·  **Status:** [ ] open
- **Exploit:** generateCode produces 4 chars from a 32-symbol alphabet = 32^4 = 1,048,576 codes, the only secret guarding a private (non-public) room. rateLimit() (index.js:40) is keyed by socket.id, so each fresh socket.io connection gets a new 30-req/10s bucket; a script opening many parallel connections (or reconnecting) resets the limiter freely. rejoin-room (line 137) has no rateLimit call at all, so code guessing via rejoin is entirely unthrottled. An attacker enumerates the ~1M space to find an active private room, then joins the open slot or (via the rejoin-room finding) takes over an in-progress match.
- **Fix:** Rate-limit join-room/rejoin-room by IP (socket.handshake.address) as well as socket.id, with a strict global cap on failed room lookups; lengthen the code or issue a one-time invite token to the room creator instead of relying on the room code as the sole private-room secret.

## [LOW] Password reset does not invalidate existing sessions
- **Area:** authn  ·  **Location:** `server/php/api/reset-password.php:28-36`  ·  **Status:** [ ] open
- **Exploit:** reset-password.php updates users.password_hash (line 29-32) and marks the token used (34-36) but touches no session state. requireAuth() (middleware/auth.php:2-9) only checks isset($_SESSION['user_id']) — there is no session_version column (confirmed absent from schema.sql) and no server-side session store keyed by user_id. An attacker holding a hijacked cookie for the victim keeps a valid session (up to the 30-day sliding lifetime in config.php) even after the victim resets their password — the standard incident-response step does not evict them.
- **Fix:** Add a users.session_version column checked in requireAuth() and stored in $_SESSION at login; bump it in reset-password.php (and any change-password endpoint) so all other sessions are rejected on next request.

## [LOW] Reset tokens stored in plaintext, usable directly from a DB read
- **Area:** recovery  ·  **Location:** `server/php/db/schema.mysql.sql:76-84`  ·  **Status:** [ ] open
- **Exploit:** forgot-password.php:31 generates $token = bin2hex(random_bytes(32)) and inserts it verbatim into password_resets.token (line 40-44); reset-password.php:19 looks it up with WHERE pr.token = :token against the raw value. schema.mysql.sql:79 stores token VARCHAR(255) NOT NULL UNIQUE with no hashing — unlike users.password_hash. Any read of the password_resets table (a future SQLi, a leaked mysqldump/backup export, misconfigured phpMyAdmin, insider DB access) yields a live, single-use, still-valid account-takeover token for any row where used=0 and expires_at>NOW(), usable with zero cracking work.
- **Fix:** Store hash('sha256', $token) in password_resets.token, keep the raw token only in the emailed URL, and look up by hash('sha256', $presentedToken) in reset-password.php. Token is single-use and 1-hour TTL, which limits the window.

## [LOW] User enumeration via response-timing side channel
- **Area:** recovery  ·  **Location:** `server/php/api/forgot-password.php:20-63`  ·  **Status:** [ ] open
- **Exploit:** Response body and status are identical for both branches (line 27 and line 63 return the same 200 JSON), correctly defeating content-based enumeration. But the code paths differ: a non-existent email returns immediately after one SELECT (line 25-28), while an existing email additionally runs a DELETE (35-37), an INSERT (40-44), and a synchronous mail() hand-off to the local MTA (line 61) before responding. The mail() call in particular can add tens-to-hundreds of ms. An attacker POSTing candidate emails and averaging latency over several samples can separate registered from unregistered addresses despite the identical response text.
- **Fix:** Make both branches perform equivalent work: run the same queries for unknown emails (or add a compensating delay) and move mail() to a queued/async dispatch so the request-path timing does not depend on account existence.

## [LOW] No rate limiting on either endpoint
- **Area:** recovery  ·  **Location:** `server/php/api/forgot-password.php:1-63`  ·  **Status:** [ ] open
- **Exploit:** Neither forgot-password.php nor reset-password.php (nor config.php) contains any throttling; a repo-wide grep for rate.limit/throttle/attempts across server/php returns nothing. An attacker scripts unlimited forgot-password POSTs against one victim email as an email-bombing / harassment vector (each request triggers a real mail() send at line 61), and can run the timing-enumeration probe above at unlimited speed to sharpen its statistical signal. Token brute force stays infeasible regardless (256-bit token), so this does not enable takeover on its own.
- **Fix:** Add per-email and per-IP throttling on both endpoints (e.g. max N forgot-password requests per email per hour and a generic IP rate limit).

## [LOW] X-Frame-Options set only via <meta http-equiv>, which browsers ignore
- **Area:** config  ·  **Location:** `index.html (+ clans/, admin/, leaderboard/, register/, profile/, profile/edit/, forgot-password/, friends/, play/, login/ index.html):7`  ·  **Status:** [ ] open
- **Exploit:** Technical claim is TRUE: X-Frame-Options is honored only as an HTTP response header; the <meta http-equiv> form is ignored by all major browsers, and I confirmed no server-level header exists (no root .htaccess; config.php jsonResponse() sets no XFO/CSP). So the static pages carry zero enforced frame protection and can be iframed by attacker.com. HOWEVER the described exploit (clickjacking authenticated profile/friend actions) is largely defeated in practice: the session cookie is SameSite=Strict (config.php:5-11), so it is NOT sent when skorchthegame.com is loaded inside a cross-site iframe. The framed page therefore renders unauthenticated, and any state-changing click is also a cross-site request without the cookie and is rejected. Residual impact is limited UI-redressing of unauthenticated views only.
- **Fix:** Emit the real header from the web server / PHP: add `Header always set X-Frame-Options "DENY"` (or better `Content-Security-Policy: frame-ancestors 'none'`) in a root .htaccess, and add it in jsonResponse(). Keep the meta tag only as harmless legacy fallback. Low priority given SameSite=Strict already blocks the authenticated-action attack.

## [LOW] No Content-Security-Policy, HSTS, or X-Content-Type-Options anywhere in the stack
- **Area:** config  ·  **Location:** `server/php/config.php:41-55`  ·  **Status:** [ ] open
- **Exploit:** Confirmed by reading jsonResponse() (config.php:41-55): it sets Content-Type, Cache-Control, Pragma, Expires, Vary, and CORS only — no CSP, no Strict-Transport-Security, no X-Content-Type-Options. Grep across all HTML heads finds none either, and there is no root .htaccess to add them (only server/php/db/.htaccess). Impact is defense-in-depth: without CSP any future XSS has unrestricted blast radius; without nosniff the user-uploaded avatars under server/php/uploads/ could be MIME-sniffed; without HSTS a first bare-http:// request is exposed to SSL-stripping despite Secure cookies (config.php:8). No confirmed XSS or content-type sink in current scope, so these are hardening gaps, not an active break.
- **Fix:** Add `header('X-Content-Type-Options: nosniff');` and an API-appropriate CSP (e.g. default-src 'none') in jsonResponse(); at the static-site/.htaccess level add Strict-Transport-Security (max-age=31536000; includeSubDomains), nosniff, and a real CSP with frame-ancestors 'none'.

## [INFO] Timing side-channel enables username enumeration on login
- **Area:** authn  ·  **Location:** `server/php/api/login.php:24`  ·  **Status:** [ ] open
- **Exploit:** Line 24 `if (!$user || !password_verify($password, $user['password_hash']))` short-circuits, so the slow bcrypt call runs only when a user row exists. A latency-measuring attacker can distinguish 'no such user' from 'user exists, wrong password' despite the identical 401 body.
- **Fix:** Always run password_verify against a precomputed dummy hash when no user is found so both paths take equivalent time, then decide on $user separately.
